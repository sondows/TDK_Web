# TDKQRS TV-7A — QR order verification model and schema preflight

Date: 2026-11-26

## Findings

- The QRS client submits a fresh request ID and cart to `POST /api/qr/table-orders`.
- That API validates the QR customer session, current table QR, menu and cart, then creates the `qr_orders` PENDING row and its items in one transaction. It has no TV-6 code verification step today.
- `qr_orders.client_request_id` is unique and can support order idempotency.
- POS/HOS staff review is handled by `PATCH /api/pos/qr-table-orders`; acceptance binds the QR session to a table session and rejection marks the QR order REJECTED.
- Normal dine-in session closure is `PATCH /api/table-sessions/[sessionId]`.
- Existing TV-6 issues a shared rolling code with a 10-second display TTL and exposes a status object. QRS must not receive the code from an API response.
- `qr_table_order_claims` and its helpers exist in source, but the read-only TEST DB inspection found the table absent. This table is required for one atomic representative candidate per table.

## Schema/model prepared

The migration adds the missing representative-claim table idempotently and a per-request `qr_order_auth_attempts` table. An attempt is bound to one QR session, table, client request ID, TV issuance, and stable cart fingerprint; it tracks private code snapshot, expiry, up to three failures, verification/consumption state, and the resulting QR order. The proposed individual attempt lifetime is two minutes, separate from TV-6's rolling 10-second display lifetime. Customer APIs must never expose the stored code.

Rate policy prepared: up to 5 newly issued attempts per QR session and 20 per table in a rolling 10-minute window. Reusing a request ID must return its existing attempt and must not extend TV display TTL. Cart fingerprints are canonicalized so item/option order alone does not change identity.
