## B. POS server error

- `src/app/pos/page.tsx` checks the staff session, then awaits a group of layout/session/catalog/settings queries. It next awaits `loadQrTableIndicators()` and `loadQrOrderNotificationCursor()`, then continues with orders, payments, and inventory before rendering `PosShell`. An uncaught failure in any awaited operation aborts the server component render and can produce the reported generic page error.
- Both QR indicator SQL statements from the current source executed successfully on TEST and production in stage 1, so a present-day `qr_sessions.table_id` 1054 error is not reproduced. Other query failures, authentication/session problems, and a different running build remain possible. POS GET also invokes `ensureRiceBusinessDay` in a transaction, so an authenticated production page request was intentionally not used as a read-only test.
- The POS and HOS failures could share the QR indicator query or DB connectivity. The historical English HOS message is consistent with a pre-`b9d7ab2` image; it does not prove whether `table_id` was missing when that image ran. No historical error log or timestamp was obtained. POS cause: unconfirmed.
- Stage 3 change is conditional on a logged failing query and matching runtime commit. If only QR indicator query fails on a verified deployed build, repair that exact SQL/schema or ordering mismatch. Keep failure visible; do not replace failed QR data with an empty successful result. If another initial query fails, repair its specific cause.

## C. HOS table list error

- `src/app/hos/page.tsx` authenticates HOS staff and reads the idle setting. The client calls `GET /api/hos/tables`; that route returns 401 for no HOS staff, or calls `loadHosTables()` and returns 503 on error. The loader's first `Promise.all` includes base tables, open sessions, merges, settings, `loadQrTableIndicators()`, and `loadCurrentPendingQrOrderCount()`. One rejected query rejects the whole list. The old HOS UI then displayed both the API error and an empty-table label; `b9d7ab2` changed this presentation and expanded server error logging.
- Both shared QR SQL queries now execute on both DBs. The historical 503 root query and MariaDB code remain unconfirmed without the NAS log. Do not weaken the 503 or fabricate tables. Stage 3 should use the existing structured log fields and fix only the logged failing dependency.

## D. 8T cancellation

- `src/app/api/table-cancellations/route.ts` previews a scope, then on confirmed cancellation rechecks staff/PIN and opens a transaction. It locks the base OPEN table session, group sessions, merges, and scoped sessions. It deduplicates session IDs and table IDs with `Set`; QR scope is `session_id IN (...) OR table_id IN (...)`, with a branch that omits the table-ID predicate when no table IDs exist. `inArray` supplies bound SQL values. It checks PENDING QR orders and completed POS orders before cancelling items/orders/table sessions, closing active QR sessions, revoking invites, and cancelling orphaned unpaid checkouts in the same transaction. A thrown database error rolls back the transaction.
- The same table-ID concept is used in checkout and explicit table-session closure. It intentionally includes unbound QR sessions belonging to the table; another table is outside the scope. Historic 8T failure could be a missing column at that time, another SQL/constraint error, or a state conflict. The current production and TEST table 8 have no open table session, QR session, or pending order, so the historic request cannot be reproduced from present rows. No cancellation was submitted.
- Stage 3 test design: use isolated TEST fixtures and transaction rollback for no QR, one unbound QR, bound/accepted QR, multiple/guest QR, unrelated-table QR, PENDING-order block, and repeated cancellation. Capture generated SQL and bind values for empty and nonempty ID arrays. Assert rollback and unaffected unrelated rows. Change only a confirmed defect.

## E. QRS URL and customer session

- `src/lib/admin-qr-export.ts::publicQrUrl` and the SVG image route build `/q/{identifier}` from `QR_PUBLIC_BASE_URL`, or else the request's forwarded Host/protocol or direct Host/origin. If an admin generates/downloads a QR over an internal-IP request without a configured canonical public base URL, the QR payload will contain that internal origin. This is a confirmed code path; the actual printed QR image and NAS environment value were unavailable, so the specific sticker payload is unconfirmed.
- An internal IP in a QR code can explain a customer's internal-IP navigation and HTTPS certificate failure. The QR entry route creates an ACTIVE row with `table_id` inside a transaction, then redirects to `/qrorder/order`, `/qrorder/join-required`, or `/qrorder` and sets a same-origin HttpOnly cookie. The redirect keeps the scanned request origin. A different public-domain visit cannot reuse an internal-IP cookie. The exact cause of the reported public-domain white screen remains unconfirmed without its HTTP response, browser console/network record, and server log.
- The QR order screens catch title/notice read failures, then client components call the QR APIs. QR token resolution checks ACTIVE status, table/sticker status, open bound session, and expiry and updates `last_active_at` for a valid token. No production QR route was invoked because it can create or mutate a session.
- Stage 3 confirmed code improvement, after inspecting an actual sticker and production `QR_PUBLIC_BASE_URL`: centralize QR URL construction so both PNG/export and SVG use one validated HTTPS public origin (`https://tdkon.myasustor.com`) instead of silently inheriting an internal Host. Preserve `/q/{identifier}`; the `/tdkqrs/` path change is out of scope. Do not reissue QR identifiers as a side effect. If the white screen persists on the public origin, diagnose that separate HTTP/client failure before editing its UI.
