## Existing COMPLETE paths and change

- `PATCH /api/table-sessions/[sessionId]` closes a dine-in visit after checking pending QR orders. It already closed customer QR sessions and revoked invites. It now locks and rechecks the exact visit after the dining-table lock, then clears the visit's representative claim and blocks its unused PENDING/VERIFIED auth attempts inside the same transaction. A repeated request for the old visit returns 409 without touching a later visit.
- `POST /api/checkouts` with `action: COMPLETE` is the POS checkout completion path. It already closes the table visit, customer QR sessions, and invites. It now obtains dining-table locks before completing, and performs the same representative/attempt cleanup in that transaction. `PAY` without COMPLETE keeps the visit and representative claim active.
- The shared cleanup is gated to a development server using `TDK_POS_TEST`, including a runtime database identity check. If that check fails while the development TEST path is active, the completion transaction fails rather than leaving a closed visit with an active claim. Cleanup is independent of the opt-in feature flag so an existing test claim can still be retired when that flag has been turned off. The helper does not query TV-7 test-only tables in production.
- QR and POS order, approval, checkout, and payment history are retained by application completion. The test harness removes only its own synthetic fixture data afterward.
