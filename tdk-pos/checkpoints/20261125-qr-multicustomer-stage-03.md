# QR 주문 개편 3단계 개발 결과 — 2026-11-25

## 범위와 판정

개발 DB `TDK_POS_TEST`에서 권한 출처를 전환하고, 다중 고객 QR 주문과 승인 기반 전체 내역 조회를 구현했다. 핵심 DB/API 통합 검증은 통과했다. 4단계 UI 작업은 시작할 수 있다. 운영 DB와 NAS에는 반영하지 않았다.

## DB 마이그레이션

- 실행 전 `SELECT DATABASE()`로 `TDK_POS_TEST`를 확인했다. 승인된 네 컬럼은 조사 시점에 이미 존재하고 형식도 일치했으므로 ALTER는 실행하지 않았다. 애플리케이션 계정에도 ALTER 권한이 없다.
- 별도 SQL 기록: `db-migrations/20261125_qr_session_access_grants_test.sql`.
- 실제 데이터 전환은 트랜잭션과 예상 건수 검증 후 커밋했다. 전환 직전 총 57건, 연결 27건, 미연결 30건, 출처 값이 있는 행 0건이었다.
- 동일 고객 QR 세션이 제출한 `ACCEPTED` QR 주문, 연결 POS 주문과 동일 이용 회차 및 동일 테이블을 직접 확인할 수 있는 17건만 `ORDER_APPROVED`와 근거 주문 ID로 분류했다.
- 초대 수락 기록은 0건이며 수락자 식별 기록이 없어 `INVITED`로 소급 분류하지 않았다. 나머지 연결 10건은 `LEGACY`로 분류했다. 미연결 30건은 출처 없이 유지했다.
- 최종 연결 분포: `ORDER_APPROVED` 17건(열린 회차 1, 닫힌 회차 16), `LEGACY` 10건(열린 회차 1, 닫힌 회차 9). 닫힌 회차는 인증 질의에서 제외된다.
- 기존 QR 토큰 해시, 주문, 결제, 세션 ID는 변경하지 않았다.

## 구현

- `src/db/schema.ts`: 권한 출처·근거 ID·부여 시각을 ORM 모델에 추가했다.
- `src/app/tdkqrs/[identifier]/route.ts`: QR 최초 스캔 시 자동 이용 회차 연결과 기존 고객 독점/초대 요구 분기를 제거했다. 활성 QR을 스캔한 고객은 독립 토큰으로 주문 화면에 진입한다.
- `src/lib/qr-order-auth.ts`: 전체 내역 권한은 열린 동일 테이블 이용 회차와 `ORDER_APPROVED`의 실제 승인 주문, `INVITED`의 수락 초대, 또는 기존 `LEGACY` 기록이 있을 때만 인정한다. 출처 문자열만 맞고 근거가 없으면 거부한다.
- `src/app/api/qr/table-orders/route.ts`: 열린 테이블의 미연결 고객도 독립 `PENDING` 주문을 제출한다. 승인 전에는 본인 요청만 반환하고 POS 주문·합계·조리 정보는 반환하지 않는다.
- `src/app/api/pos/qr-table-orders/route.ts`: 기존 열린 이용 회차를 재사용한다. POS 주문 생성, QR 승인 및 제출 고객의 `ORDER_APPROVED` 권한 기록은 같은 트랜잭션에 있다. 다른 고객 토큰은 연결하지 않는다. 중복 승인과 중복 열린 회차를 차단한다.
- `src/app/tdkqrs/join/[token]/route.ts`, `src/app/api/qr/order-invites/route.ts`: 유효 초대 합류 고객에게 `INVITED`, 초대 ID, 부여 시각을 기록하고, 초대 발행 권한도 검증된 전체 조회 권한으로 제한한다.
- `src/lib/qr-processing-policy.ts`, `src/lib/qr-processing-policy.test.mjs`: 기존 첫 고객 독점 조건을 제거했다.
- `src/app/qrorder/order/page.tsx`, `src/app/qr/QrMenuClient.tsx`: 서버가 확인한 테이블 ID로 장바구니 저장 키를 분리했다. 원문 보안 토큰은 localStorage에 저장하지 않는다. 기존 전역 장바구니 데이터는 출처 테이블을 증명할 수 없어 새 테이블 키로 복사하지 않는다.
- `src/app/qrorder/QrOrderHistory.tsx`: 승인 전 고객도 주문하기 버튼을 사용할 수 있게 했다.

## 실행한 검증

- `tests/qr-multicustomer-db.integration.mjs`: TEST 전용 임시 테이블·QR·직원 신뢰 세션을 만들어 실제 로컬 HTTP 경로를 검증하고 삭제했다. 두 고객 동시 스캔과 동시 POST, 각자 PENDING 조회, 원래 POS 선주문 내역 차단, POS 및 HOS 개별 승인, 기존 이용 회차 재사용, 두 주문 동시 승인, 중복 승인 409, 승인 고객만 전체 POS 주문·합계 조회, 정상 초대/근거 ID, 만료 초대 신규 합류 차단, 승인·초대 근거 불일치 차단, QR 폐기 후 기존 승인 고객 접근 유지, 미처리 QR 주문의 테이블 종료 차단, 승인/종료 동시 요청, 종료 후 접근 차단을 통과했다. 전체 테스트용 임시 테이블/QR 잔여 0건을 재확인했다.
- `tests/qr-code-preparation-db.integration.mjs`: 2단계 준비/활성화, 중복 준비, 주문/활성화 행 잠금 경합, 준비 QR 접속 차단, 활성 QR 발급을 재검증했다. 고정 테스트 테이블이 부족해 두 격리 시나리오는 임시 테이블을 생성하고 삭제하도록 보완했다.
- TypeScript 검사 통과, 관련 ESLint 통과, QR/인쇄/접근 정책 테스트 33건 통과, API 접근 테스트 19건 통과, Next.js 프로덕션 빌드 통과. 빌드에는 기존 메뉴 이미지 경로 추적 경고 2건이 남아 있다.

## 미검증과 운영 전 확인

- 실제 Android/iOS 브라우저에서 테이블 간 장바구니 저장 및 화면 전환은 검증하지 못했다.
- 실제 결제 장치/영수증, 실제 KDS 조리 작업, 운영 HOS/POS 화면과 운영 데이터는 검증하지 않았다. 개발 테스트는 합성된 POS 선주문과 직원 신뢰 세션으로 API를 호출했다.
- 새 이용 회차가 없는 테이블의 첫 QR 승인 경로는 프로덕션 빌드·코드 검사만 수행했다. TEST DB의 시작 준비금 정책이 활성화되어 있지만 오늘 등록 건이 0건이므로, 전역 영업 데이터를 임시로 만들지 않고 실제 HTTP 생성 시나리오는 실행하지 않았다.
- 주문 승인과 현장 QR 활성화의 정확한 동시 경합은 별도로 실행하지 않았다. 2단계 테스트에서 미처리 주문과 QR 활성화의 행 잠금 경합은 확인했다.
- 인쇄 QR을 외부인이 촬영하면 PENDING 요청을 보낼 수 있다. 직원이 허위 주문을 승인하면 그 요청자가 전체 내역을 볼 수 있으므로 승인 화면에서 테이블·주문자 확인을 강조하고 테이블별 요청 속도 제한 및 이상 징후 기록을 후속 보완으로 검토해야 한다. 현재 같은 출처 검사와 `client_request_id` 중복 방지는 있으나 명시적인 요청 빈도 제한은 없다.

운영 DB `TDK_POS`, NAS, Docker/Caddy, 실제 QR, 실제 주문에는 변경이 없다. Git 커밋·푸시도 하지 않았다.
