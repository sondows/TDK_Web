# TDKON 긴급 복구 4.5/5 — 초대 합류 수정과 배포 안전성

기준일: 2026-11-22 (KST). 1~4단계 보고서와 현재 브랜치 `main`/HEAD `b9d7ab256964218eb88642954f5a8d4c20bc3d8f`를 다시 대조했다. 이번 단계에는 운영 DB `TDK_POS`, NAS, Docker/Caddy 서비스, 운영 QR 세션을 변경하지 않았다. 기존 미커밋 작업과 실제 Git 인덱스를 보존했으며, 커밋·푸시·배포를 하지 않았다.

## A. QR 초대 합류 오류

- **원인 확인:** `src/app/q/join/[token]/route.ts`는 초대 토큰·테이블·정원·만료를 확인하고 QR 세션을 DB에 기록한 뒤 `Response.redirect(...).headers.append("Set-Cookie", ...)`를 호출했다. Node 22의 이 리다이렉트 응답 헤더는 불변이라 `TypeError: immutable`이 난다. 기존 catch는 초대 실패 화면으로 이동시켜, DB에는 활성 합류 세션이 남고 브라우저에는 인증 쿠키가 없는 상태가 가능했다.
- **수정:** `src/lib/qr-order-auth.ts`에 `qrSessionRedirectResponse()`를 추가했다. `Location`과 `Set-Cookie`를 함께 지정한 새 302 응답을 만들며, 기존 `qrSessionCookieAttributes()`를 그대로 사용한다. 일반 QR 진입과 초대 합류가 같은 함수를 호출한다. 두 경로 모두 **트랜잭션 안에서 응답 객체를 구성**하므로 응답 생성 중 예외가 나면 세션 삽입도 롤백된다. 트랜잭션 커밋 후의 네트워크 전송 실패까지 DB에서 감지하거나 되돌릴 수는 없으며, 고객이 응답을 못 받으면 새 세션이 남을 가능성은 여전히 있다. 기존 토큰 유효기간과 서버 측 만료/종료 검사가 그 세션의 이용 가능성을 제한한다.
- **추가 보호:** 초대 대상 테이블에 현재 `IN_USE`인 `TABLE_ORDER` QR 코드와 테이블 링크가 있는지 같은 트랜잭션에서 확인한다. 스티커가 잠기거나 연결이 없어져 새 쿠키만 발급되고 곧바로 인증이 거부되는 상황을 막는다. 이미 존재하는 주문·정상 세션·토큰 정책은 변경하지 않았다.
- **개발 통합 테스트:** `TDK_POS_TEST` 임시 테이블/QR/승인된 루트 주문/초대 행으로 유효 초대→302 `/qrorder`→쿠키→테이블 연결→메뉴/주문 조회→고객 주문 POST와 PENDING 행→테이블 종료 후 접근 거부까지 통과했다. 잘못된 형식, 존재하지 않음, 만료, 회수, 비활성 테이블, 잠긴 QR 스티커, 종료된 테이블, 다른 테이블 스캔, 쿠키 없는 접근도 검증했다. 거부 요청이 새 QR 세션을 만들지 않는지 확인했다. 테스트 행은 정리됐다. DB 오류 강제 주입, 실제 네트워크 전송 실패, 실제 브라우저 렌더는 수행하지 않았다.

## B. QR 보안 정책

- 고정 스티커의 16자리 식별자는 공개 라우팅 값이다. 고객 인증 토큰과 초대 토큰은 별도로 32바이트 난수에서 발급되며 DB에는 SHA-256 해시만 저장한다. 테스트에서 쿠키 토큰과 저장 해시가 다르고 해시가 일치하는지 확인했다.
- 초대는 토큰 형식, 해시 조회, 만료/회수, OPEN 테이블, 활성 테이블·현재 QR 링크, 현재 세션 기준 6시간 만료, 정원 상한을 검사한다. `redeemed_at`은 최초 사용 시각으로 기록된다.
- **기존 재사용 정책 확인:** 같은 고객의 중복 접속은 새 세션 없이 기존 `/qrorder`로 이동한다. 다른 고객은 만료되지 않은 **같은 초대 URL**로 정원이 허용하는 동안 추가 합류할 수 있다. 실제 코드와 통합 테스트에서 확인했다. `src/db/schema.ts`의 “one-time” 주석은 실제 동작과 다르다. 초대를 1회용으로 바꾸면 일행 공유 흐름이 달라지므로 이번 단계에서 임의로 변경하지 않았다. 5단계에서 의도된 정책인지 확인해야 한다.
- 쿠키는 `Path=/`, `HttpOnly`, `SameSite=Lax`, 최대 6시간이며 초대 만료 잔여 시간보다 길지 않다. `x-forwarded-proto=https`인 개발 요청에서 `Secure`를 확인했다. 실제 NAS Caddy의 HTTPS 헤더 전달은 미확인이다. 다른 테이블의 QR 스티커를 기존 고객 쿠키로 스캔하면 거부되고, 닫힌 테이블 세션의 주문 조회도 거부됐다.
- 초대 링크 생성 API는 여전히 요청 origin으로 `/q/join/{token}`을 만든다. 내부 IP에서 공유하면 내부 주소가 포함될 수 있다. 고정 QR URL 수정과 별개이며 이번 단계에서 주소 정책을 바꾸지 않았다.

## C. 배포 스크립트와 대상 범위

- 수정: 루트 `deploy.bat`는 `tdk-pos/deploy/release.ps1`만 실행한다. 기존의 `git add -A`, `git commit --only`, `git push`를 제거했다. 로컬 승인 SHA·NAS 기준 SHA·승인 파일 목록을 요구하고, Git 경로 변경 목록과 정확히 비교한다. 배포 경로 외 커밋 차이와 배포 경로의 미커밋 파일이 있으면 중단한다. 사용자의 실제 스테이징 영역을 수정하지 않는다.
- `release.ps1`은 임시 Git 인덱스에서 `git read-tree <approved SHA>`와 기존 **`Validate staged deployment paths`** 성격의 `git diff --cached --check <NAS base SHA> -- deploy.bat tdk-pos`를 수행한다. 검사를 우회하지 않는다. `DryRun`에는 SSH·원격·Docker·DB 호출이 없다. 실제 `Deploy`에는 SHA 재확인, 승인 경로 manifest, 현재 `origin/main`의 일치, 사용자 재입력이 필요하다.
- NAS 실행용 `tdk-pos/deploy/nas-release.sh`는 **승인된 Git SHA의 `git archive`**를 독립 임시 빌드 디렉터리에 풀어 Docker 이미지를 만든다. NAS 작업 트리의 미커밋 문서/테스트가 빌드에 섞이지 않는다. `.dockerignore`는 체크포인트 문서·배포 도구·테스트 파일을 Docker 빌드 컨텍스트에서 제외한다. Dockerfile에 필요한 `scripts/verify-runtime-files.cjs`와 앱 정적 파일은 제외하지 않았다. 실제 Docker 컨텍스트 생성은 로컬 Docker 부재로 미검증이다.
- 실제 작업 트리 드라이런은 변경 파일 목록과 스테이징 검사 `PASS`를 보여준 뒤 미커밋 파일 때문에 **예상대로 종료 코드 1로 중단**했다. 별도 임시 Git 저장소의 깨끗한 두 커밋/승인 manifest로 정상 드라이런을 실행해 종료 코드 0, 승인 목록 일치, 원격 호출 없음까지 확인했다. 임시 저장소를 정리했고 실제 Git 인덱스는 비어 있다.
- 5단계는 현재 미커밋 파일을 승인 대상별로 검토한 뒤 깨끗한 별도 릴리스 체크아웃과 정확한 커밋/manifest를 만들어야 한다. 현재 HEAD는 3단계와 이번 수정 코드를 포함하지 않으므로 배포 SHA가 아니다. NAS 실행 커밋이 미확인이어서 최종 파일 delta도 아직 확정할 수 없다.

## D. Docker 이미지 보존과 롤백

- `nas-release.sh`는 NAS에서 컨테이너의 **현재 실행 이미지 ID**와 생성 시각, 컨테이너 ID/생성 시각, NAS 기준 SHA를 기록한다. 릴리스 SHA별 제한된 백업 디렉터리에 이전 이미지 `docker save` 아카이브와 SHA-256, 실제 Compose/.env 설정을 보존한다. 기존 백업이 있으면 이미지 ID·기준 SHA·체크섬을 확인한 경우에만 재사용한다. 새 이미지는 Git SHA label 및 별도 후보 태그를 갖고, 검증 뒤에만 서비스 태그로 바뀐다.
- 빌드/소스 갱신/백업 오류가 나면 현재 실행 컨테이너를 교체하지 않는다. 새 컨테이너 시작 또는 헬스 오류 시 저장한 이미지·설정으로 앱 컨테이너만 자동 복구하고 이전 이미지 ID/헬스를 확인한다. 배포 후 POS/HOS/QRS 기능 오류가 나면 담당자가 `sh deploy/nas-release.sh rollback <APPROVED_SHA>`를 실행하는 절차를 마련했다. DB, 주문, 결제, QR 세션, 마운트 볼륨, Caddy 설정은 롤백에서 건드리지 않는다.
- **검증 한계:** 로컬에 Docker CLI가 없고 NAS SSH 인증이 거부돼 실제 이미지 아카이브, 후보 빌드, 컨테이너 교체, 자동/수동 롤백을 실행 검증하지 못했다. 쉘 구문 검사만 통과했다. NAS의 비대화형 `sudo -n`, 디스크 공간, 백업 경로, Compose 버전, 기존 이미지 보존 가능성, 운영 DB 백업·격리 복원 기록도 미확인이다. 이미지 태그 변경이나 헬스 성공만으로 업무 복구 완료로 판단하지 않는다.
- 롤백 후 NAS Git checkout은 신규 커밋을 가리킨 채 이전 이미지가 실행될 수 있고, 복구한 Compose 파일이 checkout을 dirty하게 만들 수 있다. 다음 배포 전에 이 상태를 별도로 대조해야 한다. 롤백 절차는 `git reset --hard`나 운영 작업 트리 청소를 실행하지 않는다.
- 구체적인 승인 입력과 명령은 `deploy/EMERGENCY-RELEASE-4_5.md`에 작성했다. `NEXT_PUBLIC_DEVICE_AGENT_URL`을 명시적으로 전달하게 해 POS 장치 연동 빌드 인자가 암묵적으로 바뀌지 않도록 했다. Caddy/환경변수 실제값은 변경하지 않았다.

## E. NAS 조사

- 비대화형 읽기 전용 SSH를 `sondows@192.168.0.83:22`에 다시 시도했으나 `Permission denied (publickey,password,keyboard-interactive)`였다. 실행 컨테이너·불변 이미지 ID·배포 커밋·11월 21~22일 POS/HOS/8T/QRS 로그를 확보하지 못했다. 비밀번호/개인키는 출력하거나 추측하지 않았다.
- 사용자가 NAS에서 직접 실행할 `docker compose ps`, `docker inspect`, Git SHA, 빌드 ID, 환경변수 **상태만** 확인하는 명령과 민감정보를 제거한 로그 수집 방법은 4단계 보고서 A절에 있다. SSH 계정·공개키 등록, `sudo -n` 권한, Caddy 프록시 헤더, QR 공개 주소 설정, 실제 인쇄 QR 페이로드를 확인해야 한다.

## G. 5단계 판단 — **조건부 진행**

초대 합류의 확인된 `TypeError: immutable`은 수정되고 개발 HTTP 통합 테스트를 통과했다. 승인되지 않은 파일의 자동 스테이징·커밋·푸시도 제거했고 로컬 드라이런에서 보호 동작을 확인했다. 따라서 **5단계의 NAS 증거 수집과 릴리스 준비는 진행할 수 있다. 실제 운영 배포는 아직 금지한다.**

운영 적용 전 필수 조건: (1) NAS 실행 이미지/커밋·오류 로그 확보와 POS/HOS/8T 원인 판단, (2) 초대 URL 재사용 정책과 내부 IP 초대 링크의 허용 범위 결정, (3) 승인된 전체 릴리스 SHA·경로 manifest 및 NAS 기준 SHA 확정, (4) 기존 이미지/설정/운영 DB 백업과 복원 가능성 검증, (5) NAS에서 후보 빌드·롤백 절차 및 Device Agent·Caddy/쿠키 설정 확인, (6) 사용자 명시적 운영 승인. 이 조건이 충족될 때까지 `deploy.bat -Mode Deploy`를 실행하지 않는다. 운영 DB 마이그레이션과 `/tdkqrs/` 경로 전환은 여전히 불필요하다.
