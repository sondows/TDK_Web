# TDKQRS TV-7C — representative claim and QR order integration

Date: 2026-11-26
Status: TEST DB migration verified; API and DB integration passed. Physical mobile/TV browser checks remain pending.

## Implemented in code

- With the default-OFF development flag enabled, the existing customer QR order POST requires a VERIFIED attempt for the first order. It revalidates the session, active QR, catalog cart, attempt ownership, request ID, cart fingerprint, unconsumed state, expiry, and captured table-session ID.
- One transaction inserts the first QR order/items, creates a PENDING claim under the dining-table lock, and consumes the attempt. Failure rolls back all three changes. Duplicate client request IDs return the prior order instead of inserting again.
- Confirmed representatives can send further orders without a code only while their QR session and claim refer to the same open table session. Other customers and pending representatives are refused. Feature OFF retains the prior order flow.
- Staff approval confirms the first claim in its existing order-approval transaction; first-order rejection releases it. Rejecting a later order leaves the confirmed claim intact.
- The QRS menu uses server representative status, shows pending/other customer notices, submits the verified attempt, and refreshes representative status every five seconds. The existing cart is retained until the order POST succeeds.
- The only customer QR order INSERT in application source is in `src/app/api/qr/table-orders/route.ts`.

## Required TEST schema change

The user applied `db-migrations/20261126_qr_order_auth_session_snapshot_test.sql` to `TDK_POS_TEST` in phpMyAdmin. A read-only check from the application account confirmed `SELECT DATABASE()=TDK_POS_TEST`, `SHOW CREATE TABLE`, 16 attempt columns, 5 attempt indexes, 3 attempt foreign keys, and the two new columns: nullable unsigned BIGINT `table_session_id_at_auth` and NOT NULL unsigned TINYINT `session_snapshot_recorded` with default 0. The claim table has 7 columns, 4 indexes, and 4 foreign keys. Both tables had zero rows before testing.
