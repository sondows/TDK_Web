# TDKQRS TV-7B — QR auth-code request and verification

Date: 2026-11-26

## Implemented

- Added `POST`/`DELETE /api/qr/order-auth` and `POST /api/qr/order-auth/verify`.
- The flow is enabled only when all checks pass: development runtime, `DB_NAME=TDK_POS_TEST`, `TDK_QR_ORDER_AUTH_ENABLED=true`, and a runtime `SELECT DATABASE()` result of `TDK_POS_TEST`. The default is OFF. The APIs repeat the server-side gate.
- Request creation validates the QR session, current table/QR and open table session, active TV-4 notice, and catalog-backed cart. It binds an attempt to the QR session, table, request UUID, TV issuance, and canonical cart fingerprint. The stored two-digit code is never returned to QRS.
- TV-6 issuance is reused inside the attempt transaction; repeat request IDs reuse the attempt without extending the TV display TTL. New request IDs follow TV-6 rolling issuance and the session/table rate limits.
- Verification locks the customer, attempt, notice, and TV issuance rows; it checks the active common code and matching issuance, enforces attempt expiry and three failures, and atomically persists VERIFIED. Repeated verification returns the persisted state idempotently.
- The QRS order button branches to a localized numeric two-digit modal only when the server page passes the opt-in flag. It preserves the cart on cancellation/failure/expiry and stores a request UUID plus cart snapshot for safe retries. Successful verification leaves the cart intact, displays that TV-7B has not submitted an order, and does not call `POST /api/qr/table-orders`.
- Added host access and API route manifest entries. The auth APIs are explicitly blocked on the public production hostname and allowed only through the development QR host policy.
