# 관리자 기기관리 전환 및 복구

## 전환 순서

1. 현재 DB 백업은 기존 NAS 백업 절차 그대로 수행합니다. 이 기능은 백업 설정을 바꾸지 않습니다.
2. 먼저 `TDK_POS_TEST`에 `20261029_admin_managed_devices.sql`을 적용하고 ADM 승인, KDS 로그인, 기존 KDS 세션을 확인합니다. 이 스크립트는 20261027·20261028의 누락된 KDS 스키마를 함께 생성합니다. `managed_devices`만 생성된 뒤 기존 기기 이전에서 실패한 경우에도 전체 스크립트를 다시 실행할 수 있습니다.
3. 기존 `kds_trusted_devices`의 기기 ID와 토큰 해시를 유지해 `managed_devices`로 옮깁니다. 아직 유효한 기존 기기는 최대 30일 동안 계속 사용할 수 있어 배포 직후 주방이 잠기지 않습니다.
4. 테스트 결과를 검토하고 운영 배포와 `TDK_POS` 마이그레이션은 별도 승인을 받은 뒤 진행합니다. 이 작업에서는 어떤 DB에도 마이그레이션을 적용하지 않습니다.

## ADM·HOS 기기 종류 확장

`managed_devices_add_adm_hos.sql`은 기존 `managed_devices` 테이블의 ENUM에 ADM·HOS를 뒤에 추가하고 `adm_enabled`, `hos_enabled`를 기본값 0으로 더합니다. 기존 POS/KDS 종류의 ENUM 순서, 기기 ID, 표시 코드, 토큰 해시, 권한 값은 유지됩니다. 먼저 `TDK_POS_TEST`에서 백업과 현재 `SHOW CREATE TABLE managed_devices` 결과를 확인한 뒤 이 확장 SQL을 적용하고 네 종류의 요청·승인·변경·차단을 검증합니다. 운영 DB에는 별도 승인 전 적용하지 않습니다.

ADM·HOS 권한은 현재 기기관리 등록 정보입니다. ADM 관리자 로그인은 기기 등록을 요구하지 않으며, HOS 주소 `/tdkhos`의 화면·주문 기능·인증 정책은 이번 확장에서 만들지 않습니다. 기존 KDS 로그인은 `kds_enabled`와 승인·만료 상태를 계속 검사합니다.

## 기기등록 화면의 상태와 본인 해지

기기등록 요청 시 브라우저에 HttpOnly 기기 쿠키를 설정합니다. 등록 탭은 서버에서 이 쿠키의 토큰 해시, 승인 상태 및 만료 시각을 조회하여 미등록·승인 대기·등록 기기를 구분합니다. 대기 중에는 같은 쿠키로 재요청해도 기존 요청을 반환합니다. 브라우저 저장값만으로 승인을 판단하지 않습니다.

등록 기기의 `등록 해지`는 동일 출처 요청과 해당 기기 쿠키를 확인한 뒤 해당 행을 `REVOKED`로 바꾸고 토큰 해시를 제거합니다. 연결된 KDS 세션과 현재 브라우저의 KDS 세션도 종료하고 기기·직원 쿠키를 삭제합니다. 내부망의 기기등록 면제와 실제 등록 상태는 별도로 유지됩니다. 이 변경에 추가 DB 마이그레이션은 없습니다.

## ADM 화면에 문제가 있을 때

먼저 ADM 사용 권한이 켜진 계정으로 다시 로그인하고 기기관리 페이지를 새로고침합니다. 화면만 고장났고 애플리케이션과 DB가 동작한다면 `POST /api/admin-center/devices`가 승인·거부 작업을 처리하므로, 배포 롤백 전에 애플리케이션 로그와 해당 API 응답을 확인합니다.

애플리케이션 승인 API도 사용할 수 없는 긴급 상황에서는, 승인된 운영 책임자가 기존 DB 운영 절차를 통해 아래 순서로 한 건만 복구할 수 있습니다. 이 절차는 `managed_devices` 마이그레이션이 이미 적용된 경우에만 사용합니다.

1. KDS 화면의 기기 이름, 종류, 6자리 확인번호를 실제 기기와 대조합니다.
2. DB에서 해당 확인번호의 `PENDING` 요청을 조회하고, 기기 이름·종류·요청 만료 시각을 다시 대조합니다.
3. 트랜잭션 안에서 해당 행을 잠근 뒤, 만료되지 않은 요청 한 건만 `APPROVED`로 바꿉니다. `device_code`는 `device_type`과 `device_id`로 만들고, `token_hash=request_token_hash`, `expires_at=NOW()+30일`, 권한은 확인된 종류에 맞게 설정합니다. `request_expires_at`과 `confirmation_code`는 비웁니다.
4. 변경 행 수가 정확히 1인지 확인하고, 실제 관리자 직원 ID로 `DEVICE_REQUEST_APPROVED` 감사 로그를 남긴 뒤 커밋합니다. 1건이 아니면 롤백하고 다시 조회합니다.
5. 기기 화면에서 승인 결과를 확인하고 직원 ID와 개인 KDS PIN으로 로그인합니다. 원문 토큰은 조회하거나 DB에 기록하지 않습니다.

수동 복구는 DB 접근 권한과 승인 절차를 이미 보유한 운영 책임자만 수행합니다. 복구 기록에는 요청 확인번호, 기기 코드, 관리자 직원 ID, 시각을 남기고, 정상화 후 ADM 화면에서 기기 상태와 감사 로그를 확인합니다.
